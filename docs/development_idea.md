# 生成式 AI 办公智能体平台开发想法

> Historical note: this document records the original prototype phase. The repository has since evolved into the
> LangGraph/OPA/MCP-based Duke Agent Fabric described in the root README and `docs/architecture.md`.

## 1. PRD 阅读结论

源文档：`【0525】生成式AI办公智能体平台建设方案自研建设方案.wps`

我对 PRD 的判断是：这个项目不应该被做成一个单点“AI 写公文工具”，而应该被做成一个组织级智能办公平台。它的核心不是模型本身，而是“组织知识中枢 + 六大办公智能体 + 轻量工作流 + 安全权限 + 可运营机制”。

PRD 中反复强调的主线包括：

- 面向政务办公，必须安全可控、私有化部署、数据不出域。
- 平台要统一建设知识底座、模型底座、权限体系、工作流能力，避免烟囱式工具。
- 首期业务入口是六大办公智能体：公文生成、政策问答、文件检索、会议纪要、文件分析比对、智能审校。
- 智能体不是复杂自治式 Agent，而是输入、流程、权限、输出都明确的轻量办公服务。
- 生成结果必须经过人工确认，尤其是正式公文、政策解释、会议纪要和审校结论。
- 后续应预留 OA、档案、督办、统一身份认证、业务系统等接口。

## 2. 我建议的产品定位

产品第一版应定位为“政务 AI 办公工作台”，而不是聊天机器人。用户进入系统后，应直接看到组织知识状态、六大智能体入口、当前任务处理链路、安全审计状态和阶段建设进度。

我会把用户的高频办公任务抽象成一个标准处理链路：

任务输入 → 权限识别 → 知识检索 → 智能体处理 → 规则审校 → 人工确认 → 本地导出 → 留痕归档

这样做的好处是：

- 符合 PRD 对轻量智能体、流程可控、结果可追溯的要求。
- 不把 AI 输出直接当最终结论，降低政务场景风险。
- 六大智能体可以共享同一套知识、权限、审校、导出和审计能力。
- 后续对接 OA、督办、档案系统时，有清晰的流程挂点。

## 3. MVP 范围

本次先实现一个可视化原型，重点展示“这个平台应该长什么样、核心能力如何组织、六大智能体如何协同”。由于当前仓库只有 PRD 文档，没有后端、模型服务或数据源，本轮实现不会假装已经完成真实 AI 能力，而是做一个可交互、可验证的前端工作台。

MVP 包含：

- 统一办公工作台首页。
- 六大办公智能体卡片和详情切换。
- 组织知识中枢状态视图。
- 平台五层架构可视化。
- 轻量工作流链路可视化。
- 安全审计和人工确认状态展示。
- 三阶段建设路线与 800 万投资概算分布图。

## 4. 关键设计原则

### 4.1 信息架构

首页不做营销式落地页，而做实际工作台。首屏需要同时回答四个问题：

- 当前平台服务哪些办公场景。
- 知识底座和安全边界是否就绪。
- 用户选择某个智能体后，系统会走什么流程。
- 这个项目如何分阶段建设和验收。

### 4.2 交互方式

用户通过点击六大智能体切换详情视图。详情区展示：

- 该智能体的输入来源。
- 处理流程。
- 预期输出。
- 审校与安全检查点。

这比单纯堆功能列表更接近真实工作方式。

### 4.3 工程实现

当前采用静态 HTML/CSS/JS 实现，原因是：

- 仓库里没有既有框架，静态原型交付快、依赖少。
- 可直接通过浏览器打开，便于评审。
- 后续如果进入工程开发，可以迁移为 Vue/React 或内部前端框架。

建议后续真实开发时拆成以下模块：

- `portal-ui`：统一门户、智能体工作台、任务状态、审计视图。
- `agent-orchestrator`：轻量智能体注册、流程编排、节点执行、状态机。
- `knowledge-service`：文件解析、元数据、全文检索、向量检索、权限过滤。
- `model-gateway`：本地模型服务适配、提示词模板、RAG、重排、输出约束。
- `safety-service`：敏感词、涉密风险、权限校验、日志审计、人工确认。
- `integration-service`：OA、统一身份、档案、督办、业务系统接口。

## 5. 本轮可视化交付物

本轮我实现的可视化结果放在：

- `prototype/index.html`
- `prototype/styles.css`
- `prototype/app.js`

验证脚本放在：

- `verification/visual_check.py`

这个原型不是后端系统，但它把 PRD 的建设内容转译成了一个可评审的产品形态：组织知识中枢、六大智能体、轻量流程、安全审计、阶段路线和投资分布都能在一个工作台里看到。

## 6. 下一阶段开发建议

如果进入真实开发，我建议先做“第一阶段基础能力”的工程版，而不是一次性铺满六大智能体：

1. 先完成统一入口、账号角色、知识库元数据、文件上传解析、全文检索。
2. 再接入基础 RAG 问答和公文模板辅助生成。
3. 然后实现审校规则、任务留痕、人工确认和本地导出。
4. 最后把六大智能体做成共享底座上的流程配置，而不是六套独立系统。

这样更容易验收，也更符合 PRD 的“基础底座先行、核心办公智能体落地、协同能力扩展”路径。
